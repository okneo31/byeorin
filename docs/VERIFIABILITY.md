# 검증 가능한 보안 (Verifiable Security)

> **규칙은 누구나 검증 가능하게. 권한은 아무나가 아니게.**
> 목표는 "최고의 보안"이 아니라 **누구나 확인할 수 있는 보안**이다.
>
> 확정: 2026-07-25 · 적용 범위: 벼린 전 제품군 (SW 셸 + 벼린 요세)

---

## 0. 왜 이 원칙인가

"가장 안전한 지갑"은 검증할 수 없는 주장이다. 사용자는 우리 말을 믿거나 말거나
둘 중 하나다. 그런데 이 지갑의 대상은 칩을 뜯어 확인할 수 없는 사람들이다.
그들이 실제로 기댈 수 있는 건 두 가지뿐이다:

1. **여러 사람이 같은 것을 봤다** (공개 소스·공개 사양)
2. **누가 몰래 바꿀 수 없다** (해시·서명·온체인 앵커)

그래서 **공개 검증은 가난한 사람의 감사(audit)** 다. 이 문서는 그 원칙을 구호가
아니라 확인 가능한 절차로 내려놓는다.

### 경계 — 공개하는 것과 절대 공개하지 않는 것

| 공개 | 비공개 |
|---|---|
| 규칙, 코드, 사양, 빌드 절차 | 시드·개인키 |
| 산출물 해시, 서명 인증서 지문 | 서명 **개인**키 (`byeorin-release.jks`) |
| 위협 모델과 **막지 못하는 것** | 사용자 비밀번호 |

Kerckhoffs 원칙: 키를 뺀 모든 것이 공개돼도 안전해야 한다.
반대로 **규칙을 이해 못 하게 만드는 방향(난독화)은 채택하지 않는다.** 아무도
해석 못 하는 규칙은 아무도 그것이 공정한지 감사할 수 없고, 결국 "만든 자만 아는"
중앙 권위를 재발명한다. 우리가 벤더 펌웨어를 문제 삼은 바로 그 구조다.

## 1. 지금 검증할 수 있는 것 (구현 완료)

### 안드로이드 APK

배포하는 `벼린.apk` 옆에 항상 `벼린.apk.manifest.json` 이 함께 나간다.
빌드 스크립트가 자동 생성하며, 사람이 손댈 수 없다.

담기는 값:

| 항목 | 의미 |
|---|---|
| `sha256` | 파일이 전송 중 바뀌지 않았는가 |
| `signer.certSha256` | 벼린의 키로 서명됐는가 (가짜 판별) |
| `source.commit` / `branch` | 어떤 소스에서 나왔다고 주장하는가 |
| `source.workingTreeClean` | **커밋 안 된 변경이 섞였는가** — 섞였으면 경고를 박는다 |
| `toolchain` | Node / Gradle / AGP / SDK 버전 |
| `claims` | 이 매니페스트가 **무엇을 주장하지 않는지** |

검증 (우리 서버에 아무것도 묻지 않는다):

```sh
node scripts/verify-byeorin-apk.mjs 벼린.apk 벼린.apk.manifest.json
```

```
[  OK  ] 무결성 (SHA-256)
[  OK  ] 진위 (서명 인증서)
[  OK  ] 출처 (주장)     ← 작업 트리가 더러웠으면 여기서 경고
[ SKIP ] 온체인 앵커     ← 아직 앵커를 발행하지 않았다 (§2.3)
```

`OK` / `FAIL` / `SKIP` 은 각각 **확인됨 / 확인해보니 틀림 / 확인할 수 없음**이다.
셋을 섞지 않는다 — 확인하지 못한 것에 `OK` 를 주면 도구가 사실보다 많은 것을
주장하게 된다. `FAIL` 이 하나라도 있으면 종료 코드가 1 이다.

### 공개된 서명 인증서 지문

```
303f801bb44af8c494b6e89844fbe86c36bd6f48ab404a4b6c0228fa3f103480
```

이 지문과 다른 APK 는 **벼린이 만든 것이 아니다.** 어디서 받았든 이 값으로
대조하면 된다.

## 2. 아직 검증할 수 없는 것 (정직하게)

주장하지 않는 것을 명시하는 것도 이 원칙의 일부다.

| 항목 | 현재 상태 | 왜 아직인가 |
|---|---|---|
| **재현 빌드** | ❌ **실측 확인됨** | 추측이 아니라 실험 결과다 (아래 §2.1). 같은 머신·같은 소스·같은 툴체인으로 `clean` 후 재빌드했더니 **해시가 달라졌다.** 즉 매니페스트의 `commit` 이 그 바이트를 만들었다는 **증명은 없다** — 현재는 우리 주장일 뿐이다. |
| **온체인 앵커** | 🟡 도구 완성, 미발행 | 기록기·검증기 구현 완료(아래 §2.2), 드라이런까지 실제로 돌려 확인했다. 아직 실제 앵커 트랜잭션을 내보내지 않았다 — publisher 키와 자금(앵커 1건당 **0.0013612 TTL**, 실측)이 필요하다. 발행 절차는 §2.3 런북. 그때까지는 매니페스트가 저장소에서만 검증되므로, 저장소 통제자가 과거 기록을 바꿀 수 있다. |
| **앱 내 커밋 표시** | ❌ | 푸터에 `v0.5.2 (3)` 까지만. 실행 중인 앱과 매니페스트를 커밋 단위로 대조할 수단이 없다. |
| **펌웨어 공개 정책** | ❌ | 요세 펌웨어를 공개·재현 가능하게 낼지 아직 미결정 ([SPEC F-11](../hardware/SPEC.md) 참조). |
| **APK 코드 감사** | ❌ | 무결성 ≠ 안전. 소스 감사는 별개 작업. |

### 2.1 재현 빌드 실험 (2026-07-26)

"재현이 되는지" 를 추측하지 않고 측정했다.

```
증분 빌드 직후          cd3fcb6d27264d60c63cc61575990fc541078e8d2979e3487fdbda7752575b67
gradlew clean 후 재빌드  5363e84330ca8b6d153e5e603830fb7691b6c38421f6585d6b61284ab19002dc
```

**같은 머신, 같은 커밋, 같은 툴체인인데 바이트가 다르다.** 다른 사람·다른 머신은
말할 것도 없다. 앞서 증분 빌드에서 해시가 같게 나왔던 것은 Gradle 이 산출물을
재사용했기 때문이고, 결정성의 근거가 아니었다.

이 사실이 중요한 이유: **재현 빌드 없이 하는 온체인 앵커링은 "사실" 이 아니라
"우리 주장" 을 못 박는다.** `벼린이 블록 N 에서 해시 H 를 공표했다` 는 증명되지만
`H 가 소스 S 에서 나왔다` 는 증명되지 않는다. 그래서 앵커링과 재현 빌드는
둘 다 필요하고, 각각이 무엇을 증명하는지 섞어 말하지 않는다.

### 2.2 온체인 앵커 설계 (구현 완료 · 발행 대기)

**왜 필요한가.** 이 저장소는 조금 전 force push 로 이력이 재작성됐다. 저장소를
통제하는 쪽이 과거를 바꿀 수 있다는 게 증명된 셈이다. 체인에 들어간 기록은
우리도 못 바꾼다. 앵커링이 파는 건 그것 하나다.

**옥상옥이 되지 않도록 최소한만.**

- **컨트랙트를 쓰지 않는다.** 레지스트리 컨트랙트는 감사·업그레이드 대상이 하나
  느는 것뿐 보장은 늘지 않는다. 평범한 0-value 트랜잭션의 `data` 에 텍스트 한 줄:

  ```
  byeorin:release:1|sha256=<64hex>|v=0.5.2+3|commit=<40hex>
  ```

  바이너리 대신 사람이 읽는 텍스트다 — 익스플로러에서 hex 를 풀면 그대로 읽힌다.

- **검증이 O(1).** 매니페스트에 앵커 `txHash` 를 적어 두므로 검증기는 RPC **2회**
  (`eth_chainId` + `eth_getTransactionByHash`)로 끝난다. 블록 스캔도 인덱서도 없다.
  검증기는 의존성 0 (순수 fetch) — 제3자가 아무것도 설치하지 않고 확인할 수 있다.

- **위조하려면 키가 필요하다.** 검증기가 보는 것:

  | 검사 | 어긋나면 |
  |---|---|
  | ⓪ RPC 의 `eth_chainId` 가 `anchor.chainId` 와 같은가 | `FAIL` |
  | ① tx 가 실제로 존재하는가 | `FAIL` |
  | ② `from` 이 `anchor-publishers.json` 의 publishers 에 있는가 | `FAIL` |
  | ③ `data` 에 이 APK 의 sha256 이 들어 있는가 | `FAIL` |
  | ④ 블록에 들어갔는가 (pending 아닌가) | `SKIP` + 경고 |
  | publishers 가 **비어 있어 ②를 검사할 수 없을 때** | `SKIP` + 경고 |

  매니페스트를 고쳐도 체인의 tx 를 못 만든다.

  **publishers 가 비면 `OK` 를 주지 않는다.** 검사하지 못한 것을 통과로 표시하면
  앵커가 증명하는 것보다 많은 것을 주장하게 된다. `SKIP` 으로 내리고 "이 앵커를
  누가 공표했는지 확인되지 않았다" 를 그대로 찍는다. `pending` 도 마찬가지다 —
  아직 블록에 없는 tx 는 확정된 기록이 아니다.

- **append-only.** 수정·폐기 기능을 만들지 않는다. 만드는 순간 가변성이 돌아온다.
  잘못 올린 앵커는 지우는 게 아니라 새 앵커로 덮어 설명한다.

**publisher 키 정책.** 지금은 **1개(단일 키)로 시작**한다. 이것은 약점이며 여기
명시한다 — 한 사람이 릴리스를 단독으로 공표할 수 있다. 다만 파괴력은 제한적이다:
이 키는 사용자 자산을 건드리지 못하고, 체인이 append-only 라 **과거 앵커를 지우거나
바꿀 수 없다.** 가짜를 하나 더 붙일 수 있을 뿐이고, 진짜 APK 를 가진 누구에게나
즉시 들킨다.

관리자가 늘면 **컨트랙트 없이 임계값**을 올린다: N 명이 각자 독립 주소로 같은
해시를 앵커링하고, 검증기가 k 개 이상 일치를 요구한다. 멀티시그 컨트랙트가
필요 없고, 누가 서명했는지 체인에 그대로 남는다.

**이 앵커가 증명하는 것 / 못 하는 것** (섞어 말하지 않는다):

| | |
|---|---|
| 증명함 | publisher 키를 쥔 쪽이 블록 N 시점에 해시 H 를 공표했다 |
| 증명 못함 | H 가 소스 S 에서 나왔다 — **재현 빌드(§2.1)가 없으면 이건 여전히 우리 주장이다** |

### 2.3 발행 런북 (아직 실행하지 않음)

> 아래 수치는 **2026-07-28 `https://rpc.ttl1.top` 실측**이다. 추정이 아니다.
> 가스 가격은 바뀔 수 있으므로 드라이런이 매번 현재 값을 다시 찍는다.

#### 준비물

| 항목 | 값 | 확인 방법 |
|---|---|---|
| 체인 | `chainId 7777` (`eth_chainId` = `0x1e61` 실측) | 기록기·검증기 양쪽이 대조한다 |
| RPC | `https://rpc.ttl1.top` | 응답 확인됨 (block `0x110c55` 기준) |
| publisher 주소 | **사용자가 준비** — 이 저장소에 키를 두지 않는다 | — |
| 가스 잔액 | 앵커 1건당 **0.0013612 TTL** | 아래 계산 |
| `viem` | **저장소 루트에 설치돼 있지 않다** | 아래 "알려진 걸림돌" |

**가스 계산 (실측):**

```
data 길이        147 bytes (zero 0 / non-zero 147)  ← 현재 매니페스트 기준
eth_estimateGas  0x6a58 = 27,224 gas
eth_gasPrice     0xba43b7400 = 50 gwei
baseFeePerGas    0x0  (eth_feeHistory 실측 — 최근 블록 전부 0)
────────────────────────────────────────────────
비용             27,224 × 50 gwei = 0.0013612 TTL
```

`data` 길이는 매니페스트의 `sha256`·`versionName`·`commit` 길이에 따라 달라지므로
가스도 조금 달라진다. 드라이런이 그때의 실제 값을 찍는다.
**여유를 두려면 0.01 TTL 이면 충분하다** (약 7회분).

#### 알려진 걸림돌 — `--send` 는 지금 이대로면 실패한다

`viem` 은 `apps/*` 와 `packages/wallet-sdk` 의 의존성이고 **저장소 루트에는 없다.**
pnpm 은 기본적으로 호이스팅하지 않으므로 `scripts/anchor-release.mjs` 의
`await import('viem')` 이 `ERR_MODULE_NOT_FOUND` 로 죽는다. 드라이런은 viem 을
쓰지 않으므로 영향이 없다. 발행 전에 둘 중 하나를 해야 한다:

```sh
pnpm add -w -D viem      # 루트에 추가 (package.json 이 바뀐다)
npm i --no-save viem     # 일회성, package.json 을 건드리지 않음
```

#### 순서

**1) 드라이런 — 키 없이, 무엇이 나갈지 눈으로 확인**

```sh
node scripts/anchor-release.mjs
```

찍히는 것: 페이로드 전문, `data` 바이트 수, `eth_chainId` 실측값, 가스·비용,
그리고 publishers 가 비었으면 그 경고. 여기서 페이로드의 `sha256` 과 `commit` 이
실제 배포할 APK 의 것인지 **눈으로 대조한다.**

**2) publisher 주소를 `anchor-publishers.json` 에 먼저 넣는다**

```json
"publishers": ["0x…"]
```

발행 **전에** 넣는다. 넣고 나면 기록기가 키에서 뽑은 주소가 이 목록에 있는지
확인하고, 없으면 전송하지 않고 멈춘다.
주소만 미리 확인하고 싶으면 (키 없이):

```sh
BYEORIN_ANCHOR_ADDRESS=0x… node scripts/anchor-release.mjs
```

**3) 발행**

```sh
BYEORIN_ANCHOR_KEY=0x… node scripts/anchor-release.mjs --send
```

`--send` 는 전송 직전에 ① RPC 의 chainId 가 7777 인가 ② 키의 주소가 publishers 에
있는가 ③ 잔액이 추정 비용 이상인가 — 셋을 확인하고, 하나라도 어긋나면 전송하지
않고 종료한다(exit 1).

전송 후 최대 120초(2초 × 60회) 동안 `eth_getTransactionReceipt` 를 폴링해
블록 번호까지 받아온다.

**4) 매니페스트 기록 — 스크립트가 자동으로 한다**

`--send` 가 성공하면 기록기가 `벼린.apk.manifest.json` 에 `anchor` 를 써넣는다.
**손으로 넣을 필요가 없다.**

```json
"anchor": {
  "chainId": 7777,
  "txHash": "0x…",
  "publisher": "0x…",
  "blockNumber": 1234567,
  "payload": "byeorin:release:1|sha256=…|v=0.5.2+3|commit=…",
  "note": "…"
}
```

120초 안에 블록에 못 들어가면 `blockNumber` 가 `null` 로 남는다. 그때는 나중에
익스플로러에서 확인해 손으로 채우면 된다 — 검증기는 `blockNumber` 필드를 읽지
않고 체인에서 직접 다시 본다.

**5) 재검증 — 제3자와 똑같은 방법으로**

```sh
node scripts/verify-byeorin-apk.mjs 벼린.apk 벼린.apk.manifest.json
```

기대하는 결과:

```
[  OK  ] 온체인 앵커
          tx 0x…
          chainId 7777
          from 0x…
          block 1234567
          data "byeorin:release:1|sha256=…"
```

`[ SKIP ]` 이 나오면 아직 끝난 게 아니다 — publishers 가 비었거나 tx 가 pending
이라는 뜻이고, 경고 문구에 어느 쪽인지 적혀 있다.

다른 RPC 로도 같은 결과가 나오는지 확인하려면:

```sh
TTL_RPC_URL=https://다른-ttl-노드 node scripts/verify-byeorin-apk.mjs 벼린.apk 벼린.apk.manifest.json
```

#### 실패하면 — 되돌리는 방법은 없다

**체인에 들어간 앵커는 지울 수 없다.** append-only 이므로 수정·폐기 기능이
없고, 만들 계획도 없다(만드는 순간 가변성이 돌아온다). 잘못 올렸을 때 할 수
있는 것은 **덮어 설명하는 것뿐**이다:

| 상황 | 되돌릴 수 있나 | 할 수 있는 것 |
|---|---|---|
| 전송 **전** 중단 (드라이런/사전 검사에서 멈춤) | — | 고치고 다시 드라이런 |
| 전송했으나 아직 pending | ❌ 사실상 불가 | 같은 nonce 에 더 높은 가스로 덮어쓰는 방법은 노드·mempool 상태에 달렸고 **미확인**이다. 보장하지 않는다. |
| 블록에 들어감 | ❌ **불가** | 올바른 해시로 새 앵커를 발행하고, 이 문서에 두 tx 를 **모두** 적어 무엇이 틀렸는지 설명한다. 잘못된 앵커를 숨기지 않는다. |
| publisher 키가 유출됨 | ❌ 과거 앵커는 그대로 유효 | 주소를 `anchor-publishers.json` 에서 빼고, 새 주소로 기존 릴리스를 다시 앵커링하고, 여기에 사유를 적는다. 과거 앵커는 여전히 "그 키가 공표했다" 는 사실로 남는다. |

그래서 **1) 드라이런에서 페이로드를 눈으로 대조하는 단계를 건너뛰지 않는다.**

발행 요약:

```sh
node scripts/anchor-release.mjs                       # 드라이런 (키 불필요)
BYEORIN_ANCHOR_KEY=0x… node scripts/anchor-release.mjs --send
```

커밋되지 않은 변경이 섞인 빌드는 기록기가 **거부한다** — 소스로 추적할 수 없는
산출물을 체인에 못 박으면 안 된다.

## 3. 로드맵

우선순위는 "신뢰를 얼마나 줄이는가" 순이다.

**1순위 — 온체인 앵커링.**
릴리스 매니페스트 해시를 TTL 체인(ChainID 7777)에 기록한다. 저장소를 통제해도
과거 릴리스 기록을 조용히 바꿀 수 없게 된다. 검증기는 우리 서버가 아니라 체인에
묻는다. 우리 체인이 있으므로 비용도 거의 없다. **"공개가 곧 보안"의 가장 직접적인
구현이며, 요세의 정품 증명(F-09)도 같은 앵커를 쓰게 된다.**

**2순위 — 재현 빌드.**
zip 타임스탬프 고정(`SOURCE_DATE_EPOCH`), AGP/Gradle/JDK 핀 고정, 컨테이너 빌드.
서명 전 APK 기준으로 먼저 재현성을 확보하고, 서명은 분리해 검증한다.
이게 되면 "commit → bytes" 가 주장이 아니라 확인 가능한 사실이 된다.

**3순위 — 앱 내 빌드 커밋 표시.**
푸터에 짧은 커밋 해시를 넣어, 손에 든 폰과 매니페스트를 직접 대조 가능하게.

**4순위 — 요세 펌웨어 공개 정책 확정** ([SPEC F-11~F-13](../hardware/SPEC.md)).

---

## 4. 왜 순서가 이런가

Ledger Recover(2023)가 보여준 것: "시드는 기기를 떠날 수 없다"는 **물리 법칙이
아니라 정책**이었고, 서명 권한을 쥔 벤더가 정책을 바꾸자 전제가 무너졌다.

그래서 우리가 줄여야 할 신뢰의 순서는:

1. **"우리가 배포한 파일이 맞나"** → 해시·서명 (✅ 완료)
2. **"우리가 기록을 조용히 바꾸지 않았나"** → 온체인 앵커 (1순위)
3. **"우리가 말한 소스가 진짜 그 바이너리인가"** → 재현 빌드 (2순위)
4. **"우리가 펌웨어로 규칙을 바꿀 수 있나"** → 공개 펌웨어 + 안티롤백 (4순위)

각 단계는 "벼린을 믿어야 하는 정도"를 한 칸씩 줄인다.
전부 끝나도 **칩 벤더·물리 공격·사람에 대한 공격은 남는다** — 그건
[apps/android/README.md](../apps/android/README.md) 의 위협 모델에 적어 두었다.
